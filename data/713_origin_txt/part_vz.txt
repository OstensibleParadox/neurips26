## 🎯 问题核心：认证信息打架

Claude Code和OpenClaw都在抢同一个认证资源：

```
macOS Keychain
└── "Claude Code-credentials" ← 只有一个位置！
        ├── Claude Code 要用
        └── OpenClaw 也要用
```

当OpenClaw的`settings.json`里配置了不同的认证方式，就会把钥匙串里的认证搞乱。

## 🔍 OpenClaw的settings.json长啥样（根据搜索到的资料）

第三方工具通常会这样配置[citation:2]：

```json
// ~/.openclaw/settings.json 或类似位置
{
  "providers": {
    "primary": "anthropic",
    "anthropic": {
      "apiKey": "sk-ant-xxx...",  ← API Key
      "model": "claude-3-5-sonnet-20241022"
    }
  },
  "auth": {
    "method": "oauth",  ← 或者 "api_key"
    "token": "..." 
  }
}
```

## ⚔️ 冲突是怎么发生的？

### 场景1：认证方式混用
```
Claude Code: OAuth (钥匙串里的token)
OpenClaw: API Key (settings.json里的sk-ant-xxx)

结果：OpenClaw每次启动可能刷新钥匙串，把Claude Code的认证搞乱
```

### 场景2：scope冲突
根据Anthropic的政策，OAuth token现在加了`scope: "claude-code-only"`[citation:2][citation:4]：

```json
{
  "access_token": "sk-ant-oat-xxx...",
  "scope": "claude-code-only",  ← 只允许官方Claude Code用！
  "client_id": "claude-code-official"
}
```

OpenClaw拿着这个token去请求，会被API服务器拒绝，因为`X-Client-ID`不对[citation:2]。

## 🛠️ 解决方案

### 方案A：让OpenClaw独立认证（推荐）

```bash
# 1. 查看OpenClaw的配置位置
ls -la ~/.openclaw/
ls -la ~/.config/openclaw/
ls -la ~/Library/Application\ Support/openclaw/

# 2. 找到settings.json后，改成用独立的API Key
```

在OpenClaw的settings.json里：
```json
{
  "providers": {
    "primary": "anthropic",
    "anthropic": {
      "apiKey": "sk-ant-api03-...",  ← 在console.anthropic.com单独生成
      "baseURL": "https://api.anthropic.com/v1"
    }
  },
  "auth": {
    "method": "api_key",  // 明确用API Key，不用OAuth
    "preventKeychainSync": true  // 不和系统钥匙串同步
  }
}
```

### 方案B：让OpenClaw走Claude Code的认证（但可能有风险）

有些第三方工具会模拟Claude Code客户端[citation:4]：
```json
{
  "providers": {
    "anthropic": {
      "useSystemKeychain": true,  // 用钥匙串里的认证
      "clientId": "claude-code-official",  // 冒充官方客户端
      "userAgent": "ClaudeCode/2.1.74"
    }
  }
}
```

**⚠️ 风险**：Anthropic正在严厉打击这种"伪装"[citation:4]，可能导致账号被封或认证失效。

### 方案C：完全隔离两个工具的环境

```bash
# 1. 为OpenClaw创建独立环境变量
# 在启动OpenClaw的脚本里设置
export ANTHROPIC_API_KEY="sk-ant-xxx..."  # 单独API Key
export CLAUDE_CONFIG_DIR="$HOME/.config/openclaw-claude"  # 独立配置目录

# 2. 启动OpenClaw时用这些环境变量
openclaw --config-dir ~/.config/openclaw-claude
```

## 🔍 OpenClaw的settings.json解析

看清楚了，这settings.json里**根本没有存任何认证信息**！

```json
{
  "user": {
    "default_agent": "claude",
    "default_model": "haiku",
    "allowed_tools": [],
    "provider_mode": "local",     ← 本地模式
    "auth_mode": "cli",           ← 关键在这里！
    "permission_mode": "auto_read",
    "keybinding_overrides": [],
    "onboarding_completed": true,
    "updated_at": "2026-03-12T02:40:32.445Z"
  }
}
```

## 🎯 **"auth_mode": "cli" 是什么意思？**

**这是最关键的发现！**

`"auth_mode": "cli"` 表示 OpenClaw 在说：

> "老子自己不存认证，直接**偷** Claude Code 的认证来用！"

它怎么偷的？
1. 调用 `claude auth status` 看你是不是登录了
2. 读取钥匙串里的 Claude Code 凭证
3. 或者直接继承 Claude Code 的环境变量

## ⚔️ **所以冲突是怎么发生的？**

### 场景1：OpenClaw 启动时，它会：
```javascript
// 伪代码 - OpenClaw 的内部逻辑
function getAuth() {
  if (config.auth_mode === 'cli') {
    // 调用 Claude Code 的认证
    const claudeAuth = execSync('claude auth status --json');
    return claudeAuth.token;  // ← 这里可能把钥匙串搞乱
  }
}
```

### 场景2：两个进程同时读写钥匙串
```
Claude Code 在用认证 → OpenClaw 也来读 → 钥匙串锁冲突 → 认证信息损坏
```
