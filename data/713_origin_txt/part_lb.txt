### The Short Answer
When a contract is discharged due to frustration of purpose, the **future duties** of both parties to perform are **excused**. However, the fate of the "previously articulated considerations"—things already paid or performed before the frustrating event—depends on whether a court applies the traditional common law rule or the modern restitution approach.

Here is the breakdown of how the law treats those prior considerations.

### 1. The Doctrine Applied: Frustration of Purpose
First, it is important to confirm the framework. Frustration of purpose applies when:
- A supervening event occurs.
- The parties assumed the event would not occur.
- The event destroys the **principal purpose** of the contract (the reason one party entered it).
- Neither party is at fault.

Since you state the subject matter is "fundamentally undeliverable under current clause," the contract is likely discharged as of the moment of the frustrating event.

### 2. The Fate of "Previously Articulated Considerations"
Here is how courts typically treat the elements exchanged before the discharge:

**A. Duties to Perform in the Future (Executory Considerations)**
- **Status:** These are **discharged**.
- **Explanation:** Because the purpose of the contract has been frustrated, neither party is required to continue performing. If you had not yet delivered the goods or paid the outstanding balance, you are no longer obligated to do so.

**B. Performance Already Rendered (Executed Considerations)**
This is the complex part. There is a split in legal approaches:

- **The Traditional "Loss Lies Where It Falls" Rule:**
    - Under the original common law (and English law), if the frustration occurred *after* a benefit had been conferred, the performing party could not recover the value of that benefit.
    - *Example:* You paid $10,000 upfront to rent a venue for a coronation viewing party. The coronation is cancelled. Under the old rule, the venue owner keeps the $10,000 even though the purpose is frustrated, and you owe nothing further.
    - *Status:* The payment is **retained**; the performance is **lost**.

- **The Modern Restitution Approach (US: Restatement (Second) of Contracts § 377):**
    - Modern US courts and the Uniform Commercial Code (UCC) attempt to prevent unjust enrichment. They allow a party to recover the value of the performance rendered *minus* any actual loss the other party suffered.
    - *Example:* Using the $10,000 venue fee above: If the venue owner incurred $2,000 in non-refundable catering deposits before the cancellation, they keep that $2,000. They must return the remaining $8,000 to you.
    - *Status:* The consideration is subject to **restitution**.

### 3. Distinction from Impossibility
It is important to note that you specified **frustration of purpose** rather than "impossibility" or "impracticability."

- **In Impossibility:** The subject matter is physically destroyed (e.g., the venue burns down). In that case, the duty is excused, and any money paid can usually be recovered in restitution (the person holding the money is unjustly enriched if they keep it for a service they cannot provide).
- **In Frustration of Purpose:** The subject matter exists (the venue is open), but the *reason* for the contract is gone. Because the benefit is still technically available, courts are slightly less aggressive in forcing restitution, though the modern trend favors allowing recovery of the payments to prevent a windfall.

### Summary
The "previously articulated considerations" are generally **recoverable** (or returnable) to the extent that the other party has not incurred expenses in reliance on the contract.

sudo 权限 下为什么每个命令前面的字符会变化
你观察到的这个现象，根源在于 **`sudo` 命令会切换用户身份，并随之重置 Shell 的运行环境**。其中，最直观的变化就是那个代表你身份的**命令提示符（Prompt）**，比如你熟悉的 `$` 变成了 `#` [citation:4]。

这个小小的符号背后，其实是 Linux 为了保障系统安全而设置的一道关键屏障。

简单来说，`sudo` 命令执行时会发生以下变化：

- **身份切换**：`sudo` 允许你以其他用户（默认是 `root` 超级管理员）的身份执行命令 [citation:2][citation:6]。
- **环境重置**：出于安全考虑，`sudo` 默认会先重置环境变量，为你创建一个干净、受控的新环境，防止潜在的风险通过环境变量渗透到高权限操作中 [citation:8][citation:10]。
- **配置加载**：如果使用了 `sudo -i` 或 `sudo su -` 等命令，系统甚至会模拟一次完整登录，重新加载 `root` 用户的配置文件（如 `/root/.bashrc`），让你完全进入 `root` 的工作环境 [citation:2][citation:6]。

### 1. 👑 身份变了，提示符当然要变

命令提示符通常由环境变量 `PS1` 定义。当你从普通用户切换到 `root` 用户后，`PS1` 变量的值也随之改变。最常见的表现就是提示符的结尾符号从代表普通用户的 **`$`** 变成了代表超级用户的 **`#`** [citation:4]。这就像系统在时刻提醒你："现在你拥有最高权限，操作请务必小心！"

| 用户身份 | 常见提示符 | 说明 |
| :--- | :--- | :--- |
| 普通用户 | `user@hostname:~$` | 以 `$` 结尾 |
| root 用户 | `root@hostname:~#` | 以 `#` 结尾 |

### 2. 🛡️ 背后原因：`sudo` 的安全机制

这种变化并非偶然，而是 `sudo` 的安全机制在起作用。不同的 `sudo` 用法，会带来程度不同的环境变化：

- **临时提升权限 (`sudo cmd`)**：当你执行 `sudo ls` 这样的命令时，`sudo` 会启动一个**全新的、最小化的环境**来运行 `ls` 命令。它会重置大部分环境变量，只保留极少数必要的变量（如 `TERM`），并添加一些 `SUDO_*` 开头的变量来记录原始用户信息 [citation:8]。命令执行完毕，环境随即销毁，因此你当前 Shell 的提示符通常**不会改变**。

- **切换到 root 环境 (`sudo -i` 或 `sudo su -`)**：当你想获得一个持久的 `root` 权限 Shell 时，情况就不同了。`sudo -i` 或 `sudo su -` 会模拟 `root` 用户登录 [citation:2][citation:6]。这意味着系统会读取 `root` 用户的配置文件（如 `.bashrc`），从而完整地切换到 `root` 的工作环境，包括属于 `root` 的命令提示符。这时你就能清晰地看到提示符从 `$` 变为 `#` [citation:4]。

可以理解为，`sudo` 在提升权限的同时，通过重置环境来确保安全，而提示符的变化，就是这种身份和环境切换最直观的视觉信号。

### 3. 💡 除了提示符，环境变化还会带来什么影响？

理解了这一点，就能解释很多相关现象了。比如，你可能会发现，用 `sudo` 执行命令时，有时会提示找不到某个你自定义的命令，或者程序的界面显示异常。

这通常是因为 `sudo` 重置了环境变量，导致：
- **命令找不到**：你个人设置的 `PATH` 变量没有被带到 `sudo` 环境中，系统找不到放在个人目录下的命令 [citation:3][citation:8]。
- **程序显示异常**：像 `htop` 这样的高级终端工具，可能依赖 `TERM` 等环境变量来确定终端类型和显示特性。`sudo` 重置环境后，程序可能就无法正确识别了 [citation:10]。

不过，你可以通过 `sudo` 的 `--preserve-env` 选项，或者在 `/etc/sudoers` 文件中配置 `env_keep` 列表，有选择地保留某些需要的环境变量 [citation:8][citation:10]。当然，这样做之前需要先了解潜在的安全风险。

### ✨ 一个有趣的新变化

值得一提的是，从 Ubuntu 26.04 LTS 开始，你还会注意到 `sudo` 的另一个变化：**输入密码时，屏幕上会开始显示星号（`*`）了** [citation:1]。这是 `sudo-rs`（一个用 Rust 语言重写的更安全的 `sudo` 版本）默认启用的新特性，主要是为了提升易用性，让输入密码时有更明确的视觉反馈 [citation:1]。当然，如果你更喜欢传统的“盲输”方式，也可以手动关闭它。

提示符从 `$` 变为 `#` 是身份切换的信号，密码输入出现星号是版本迭代带来的变化。如果你对 `/etc/sudoers` 的安全配置感兴趣，或者想了解如何自定义命令提示符，随时都可以问我。
how to sudo run a python script then?
Here are the standard ways to run a Python script with `sudo`, depending on your specific needs:

## 1. **Basic sudo execution** (most common)
```bash
sudo python3 /path/to/your/script.py
```
Or if the script is executable and has a shebang line:
```bash
sudo /path/to/your/script.py
```

## 2. **Navigate to directory first** (if script uses relative paths)
```bash
cd /path/to/your/ && sudo python3 script.py
```

## 3. **Preserve your environment variables** (if needed)
```bash
sudo -E python3 script.py
```
The `-E` flag preserves your current user's environment variables (like custom `PATH` settings, API keys, etc.).

## 4. **Run with specific Python interpreter**
```bash
sudo /usr/bin/python3 /path/to/script.py
```
Useful if you have multiple Python versions installed.

## 5. **Make script executable first** (one-time setup)
```bash
chmod +x script.py
sudo ./script.py
```
Ensure your script has this first line (shebang):
```python
#!/usr/bin/env python3
# or
#!/usr/bin/python3
```

## Common Issues & Solutions

### ❌ "Module not found" error
When you run with `sudo`, you're using the **system Python**, not your virtual environment:
```bash
# Check which Python pip is using
which pip3

# Install package for system Python
sudo pip3 install package-name

# Or use the exact Python path
sudo /usr/bin/python3 -m pip install package-name
```

### ❌ "Command not found" for your script
Make sure the script is in `sudo`'s PATH:
```bash
# Check sudo's PATH
sudo env | grep PATH

# Either use full path
sudo /full/path/to/script.py

# Or add to sudoers (advanced)
sudo visudo
# Add: Defaults    secure_path = /sbin:/bin:/usr/sbin:/usr/bin:/your/custom/path
```

### ❌ Script needs virtual environment
If your script depends on virtual env packages:
```bash
# Activate venv with full path to python
sudo /path/to/venv/bin/python3 script.py

# Or preserve the environment (if venv is activated)
source venv/bin/activate
sudo -E python3 script.py
```

## Best Practice Example

Here's a robust way to handle sudo Python scripts:

```bash
#!/bin/bash
# wrapper.sh - Safe way to run Python script with sudo

# Get the directory where this script is located
DIR="$( cd "$( dirname "${BASH_SOURCE[0]}" )" && pwd )"

# Run Python script with explicit paths
cd "$DIR" && sudo python3 "$DIR/script.py"
```

## Quick Decision Guide

| Situation | Command |
|-----------|---------|
| Script needs root privileges | `sudo python3 script.py` |
| Script uses relative paths | `cd /path/ && sudo python3 script.py` |
| Needs your environment variables | `sudo -E python3 script.py` |
| Uses virtual environment packages | `sudo /venv/bin/python3 script.py` |
| Wants to keep current directory | `sudo python3 $(pwd)/script.py` |
