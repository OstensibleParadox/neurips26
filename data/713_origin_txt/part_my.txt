    运行以下命令，系统会列出这张GPU支持的所有切分方式[citation:6][citation:7]：
    ```bash
    sudo nvidia-smi mig -lgip
    ```

2.  **理解Profile命名**
    输出中的`Name`列是关键，命名规则为 `MIG [X]g.[Y]gb`，例如：
    - **`1g.10gb`**：1个计算切片(Compute Slice) + 10GB显存，适合小模型推理或开发测试。
    - **`2g.20gb`**：2个计算切片 + 20GB显存，适合中等规模模型微调。
    - **`3g.40gb`**：3个计算切片 + 40GB显存，适合较大模型训练。
    - **`7g.80gb`**：整张GPU的资源，相当于没有切分[citation:1][citation:7]。

3.  **规划切割方案**
    查看 `Instances Free/Total` 列，它会告诉你这张卡最多能切出多少个该规格的实例。例如，`7/7`表示可以切出最多7个`1g.10gb`的实例[citation:6]。

### ✂️ 第三步：创建并分配MIG实例

根据你的规划，使用Profile ID创建具体的实例。

1.  **创建实例**
    假设你想把一张A100 80GB切成**1个`4g.40gb`（用于大模型）和2个`2g.20gb`（用于小任务）**。使用以下命令，`-cgi`后面按顺序列出对应Profile的ID[citation:6][citation:10]：
    ```bash
    # -cgi 参数后跟Profile ID，多个用逗号隔开，-C表示确认执行
    # 假设4g.40gb的ID是5，2g.20gb的ID是14
    sudo nvidia-smi mig -i 0 -cgi 5,14,14 -C
    ```

2.  **验证实例**

    ```text
      MIG 2: 2g.20gb (UUID: MIG-cccc-3333-...)
    ```

### 🐳 如何在Docker或K8s中使用

创建好实例后，关键就在于让容器“认领”正确的虚拟GPU。

- **在Docker中使用**：使用`--gpus`参数，并**指定完整UUID**，而不是设备序号[citation:7]。
  ```bash
  # 将容器绑定到第一个MIG实例
  docker run --gpus '"device=MIG-aaaa-1111-..."' your-image:latest
  ```

- **在Kubernetes中使用**：需要安装NVIDIA的GPU Operator。之后，你可以通过标准方式请求`nvidia.com/gpu`资源，K8s会自动将MIG实例视为独立的GPU设备进行调度[citation:5][citation:8]。

### ⚠️ 关键注意事项

1.  **切割是静态的**：一旦创建好MIG实例，如果想改变大小（比如从`2g.20gb`变成`1g.10gb`），**必须先删除所有现有实例，然后重新创建**，这个过程需要重置GPU[citation:5][citation:8]。
2.  **无法使用`--gpus all`**：在启用了MIG的GPU上，`--gpus all`会尝试将所有MIG实例分配给同一个容器，这通常不是你想要的效果。必须为每个容器指定唯一的实例UUID[citation:7]。
3.  **性能隔离**：MIG提供的是硬件级隔离，一个实例的显存爆满或计算过载，**完全不影响**同卡上的其他实例，这是它相比时间切片的最大优势[citation:1][citation:8]。

> 💡 **规划建议**：在生产环境中，可以按团队或任务类型（训练/推理）规划不同的节点池。比如，一部分节点全部切成`1g.10gb`专门跑推理服务，另一部分节点切成`4g.40gb`给算法团队做模型微调，通过K8s的节点亲和性让任务各自归位[citation:5]。

可以混用，而且这正是构建生产级多租户GPU平台的推荐方式[citation:1][citation:4][citation:8]。它们解决的是不同层面的问题，可以形成一个互补的、分层隔离的架构：

| 技术 | 解决的问题 | 类比 |
| :--- | :--- | :--- |
| **MIG (Multi-Instance GPU)** | **硬件级隔离**：将物理GPU切分成多个独立、安全的子设备[citation:2][citation:10]。 | 将一栋大楼的每一层用钢筋混凝土隔成多个独立房间，每个房间有独立的门、水电表，互不干扰。 |
| **vCluster (Virtual Cluster)** | **控制平面隔离**：为每个团队创建一个独立的、轻量级的Kubernetes控制平面[citation:4][citation:6]。 | 给每个租户一把可以独立装修和管理的“房卡”，让他们拥有自己的一整套“物业管理系统”（API server, etcd），可以随意安装自己的软件。 |
| **RBAC (Role-Based Access Control)** | **权限与策略隔离**：在Kubernetes中精细控制“谁”可以对“什么资源”做“什么操作”[citation:6]。 | 给每个房间分配专用的钥匙（权限），决定谁可以进入房间、在房间内可以开哪扇柜门。 |

简单来说，**MIG**负责在硬件底层切分GPU，**vCluster**在管理面上为团队提供“专属集群”的体验，而**RBAC**则控制他们在这个专属空间内的操作权限。

### 🛠️ 如何混合使用

这套架构的核心思想是：**在物理集群上启用MIG，将其分割成多个硬件隔离的GPU实例，然后为每个团队或项目创建一个vCluster，并配置RBAC，让vCluster能独占或共享底层的MIG设备。**

下面是具体的操作步骤：

#### 1. 在Kubernetes集群中启用MIG
这是基础步骤，确保你的节点能提供硬件隔离的GPU资源。

- **安装NVIDIA GPU Operator**：这是关键一步，它会自动化管理GPU驱动、设备插件等[citation:5][citation:10]。
- **配置MIG策略**：通过Helm安装时，设置MIG策略。
    - `--set mig.strategy=single`：将整个节点上的GPU统一切成同一种MIG设备，例如全部切成`1g.10gb`，然后作为`nvidia.com/gpu`资源暴露[citation:5][citation:10]。
    - `--set mig.strategy=mixed`：更灵活，允许在节点上创建多种MIG Profile，例如同时有`1g.10gb`和`2g.20gb`的设备[citation:5]。
- **给节点打标签**：安装完成后，通过给节点打上`nvidia.com/mig.config=all-1g.10gb`这样的标签，触发MIG Manager自动在物理GPU上创建出对应的MIG实例[citation:5][citation:7]。

#### 2. 创建并配置vCluster
现在，在你的物理集群上为各个团队创建隔离的vCluster。

- **创建命名空间**：为第一个团队创建一个独立的命名空间，例如`team-gpu-01`。
    ```bash
    kubectl create ns team-gpu-01
    ```
- **创建vCluster**：在该命名空间中创建一个虚拟集群，例如`vcluster-team-01`。
    ```bash
    vcluster create vcluster-team-01 -n team-gpu-01 --connect=false
    ```
- **在vCluster中配置RBAC**：创建完成后，你可以登录到`vcluster-team-01`这个“虚拟集群”里，用`kubectl`创建RBAC资源（如`Role`、`RoleBinding`）。这样就可以精细地控制该团队内部不同成员对资源的访问权限了[citation:6]。
- **向团队交付访问凭证**：将生成的`kubeconfig`文件交给团队负责人，他们就可以像使用一个独立集群一样使用这个vCluster。

#### 3. 让vCluster里的Pod使用MIG设备
最关键的一步是确保vCluster中的Pod能调度到正确的GPU资源上。

- **验证GPU可访问性**：首先，在vCluster中创建一个测试Pod，确保它能从“宿主机”集群继承GPU能力[citation:9]。
- **在Pod中请求GPU**：用户在提交自己的训练任务时，只需在其Pod的YAML中通过`resources.limits`请求`nvidia.com/gpu`资源即可。
    - 如果物理集群采用的是`single` MIG策略，请求`nvidia.com/gpu: 1`，调度器会自动为你分配一个完整的MIG设备（如一个`1g.10gb`的实例）。
    - 如果物理集群采用的是`mixed` MIG策略，节点上会暴露多种资源，如`nvidia.com/mig-1g.10gb`和`nvidia.com/mig-2g.20gb`。此时，用户可以根据自己任务的需求，在Pod中明确请求特定类型的资源[citation:10]。

### 📝 架构示例与最佳实践

一个典型的多租户GPU平台架构可能如下所示：

- **硬件层**：几台物理服务器，每台装有8张NVIDIA A100/H100 GPU。
- **基础设施层**：在每台服务器上启用MIG，将一张A100切成7个`1g.10gb`的MIG设备。
- **平台层**：部署一个Kubernetes物理集群，通过GPU Operator将所有的MIG设备作为可调度资源。
- **租户层**：
    - 为“算法团队A”创建一个名为`vcluster-tenant-a`的vCluster。
    - 为“算法团队B”创建一个名为`vcluster-tenant-b`的vCluster。
- **管理层**：
    - 通过Kubernetes的**RBAC**，设定`platform-admin`角色可以管理所有vCluster的生命周期。
    - 在`vcluster-tenant-a`内部，通过**RBAC**设定`lead-researcher`角色拥有对`gpu`资源的创建权限，而`intern`角色只有查看权限。
