Sysadmin 将 Docker 环境与公司其他成员隔离，主要依赖 Linux 内核的**命名空间**和**控制组**这两大核心技术，并通过在 Docker 守护进程（dockerd）中启用特定配置来实现。

### 🛡️ 核心隔离机制

1.  **用户命名空间：权限隔离的基石**
    这是实现多租户隔离最关键的技术。通过在 Docker 守护进程的配置文件 (`/etc/docker/daemon.json`) 中启用 `"userns-remap": "default"` 或指定一个用户，可以实现以下效果：
    - **UID/GID 重映射**：容器内部的 `root` 用户（UID 0）会被映射为宿主机上一个权限极低的、非特权用户的 UID（例如 UID 231072）[citation:3][citation:6]。这意味着，即使攻击者攻破了容器并取得了内部的 `root` 权限，他在宿主机上也只是一个没有任何特权的普通用户，无法对宿主机或其他容器造成破坏。
    - **文件系统隔离**：启用此功能后，每个租户（或用户）的容器镜像、容器层和卷数据都会被存储在 `/var/lib/docker/` 下的一个以该非特权用户 UID 命名的独立目录中（例如 `/var/lib/docker/231072.231072/`），从根本上实现了文件系统层面的隔离[citation:6]。

2.  **其他命名空间：资源视图隔离**
    Docker 会为每个容器创建一组独立的命名空间，让容器内的进程“看”不到宿主机和其他容器的资源[citation:1][citation:5]。
    - **PID 命名空间**：容器内的进程拥有自己独立的进程号空间，从 1 开始，无法看到或影响宿主机或其他容器的进程。
    - **网络命名空间**：每个容器拥有独立的网络栈，包括自己的网络接口、IP 地址和路由表。结合 Docker 网络，可以为每个租户创建独立的网络，例如 `docker network create tenant_a_network`，实现网络流量隔离[citation:1]。
    - **挂载命名空间**：每个容器拥有独立的文件系统挂载点视图。
    - **IPC 命名空间**：隔离进程间通信资源，如信号量和共享内存。

3.  **控制组：资源使用隔离**
    控制组（cgroups）确保某个租户的容器不会耗尽所有系统资源，影响其他租户。通过 Docker 运行命令或守护进程配置，可以对每个容器或一组容器设置精确的资源上限[citation:1][citation:5]。
    - **CPU 限制**：`--cpus="1.5"` 限制最多使用 1.5 个 CPU 核心。
    - **内存限制**：`--memory="2g"` 限制最大内存使用量为 2GB，超过可能触发 OOM（内存溢出） Killer。
    - **磁盘 I/O 限制**：`--device-write-bps` 限制写入磁盘的速率。
    - **进程数限制**：`--pids-limit=100` 限制容器内最多能创建的进程数。

### 🛠️ 实践步骤与最佳实践

1.  **在宿主机上启用用户命名空间**（核心步骤）
    - **编辑 Docker 配置文件**：创建或编辑 `/etc/docker/daemon.json`，添加以下内容[citation:1][citation:6]：
      ```json
      {
        "userns-remap": "default",
        "default-cgroupns-mode": "private"
      }
      ```
    - **重启 Docker 服务**：`sudo systemctl restart docker` 使配置生效。
    - **验证**：检查 `dockremap` 用户是否被创建，并确认 `/var/lib/docker/` 下出现了新的 UID 目录[citation:3]。

2.  **为不同团队或项目创建独立的网络**
    ```bash
    # 为“开发”团队创建一个网络
    docker network create --driver bridge dev_network
    # 为“测试”团队创建一个网络
    docker network create --driver bridge qa_network
    ```

3.  **使用资源限制参数运行容器**
    ```bash
    # 为“开发”团队运行一个受限容器
    docker run -d \
      --name dev-app \
      --network dev_network \
      --memory="1g" \
      --cpus="0.5" \
      --pids-limit=50 \
      nginx:alpine
    ```

4.  **增强安全的其他措施**
    - **以非 root 用户运行**：在 `Dockerfile` 中创建用户，或在 `docker run` 命令中使用 `--user` 参数指定非特权用户运行应用进程[citation:10]。
    - **禁用容器间通信**：在 Docker 守护进程启动参数中添加 `--icc=false`，这会禁止默认网络（`docker0`）上所有容器之间的通信，强制容器通过 `--link` 或自定义网络进行受控通信，这有助于减少攻击面[citation:7]。
    - **限制 Linux 能力**：使用 `--cap-drop=ALL` 和 `--cap-add=NET_BIND_SERVICE` 等方式，精确授予容器所需的最小系统权限[citation:10]。
    - **使用安全计算模式与安全增强模块**：通过 `--security-opt` 加载自定义的 seccomp 配置文件和 AppArmor/SELinux 策略，进一步限制容器可执行的系统调用[citation:10]。

### ⚠️ 需要注意的限制

- **特权容器不兼容**：为某个容器启用 `--privileged` 模式会自动禁用用户命名空间隔离。如果某个容器确实需要特权，必须在运行命令中额外指定 `--userns=host`[citation:6]。
- **主机命名空间共享**：如果一个容器需要共享主机的 PID 或网络命名空间（例如 `--pid=host` 或 `--network=host`），也无法使用用户命名空间隔离[citation:6]。
- **卷的权限问题**：当挂载主机目录（绑定挂载）时，需要确保主机上目录的权限与重映射后的非特权用户（如 UID 231072）相匹配，否则容器内可能会因权限不足而无法读写文件[citation:6]。

### 💎 总结

| 隔离维度 | 核心技术/配置 | 作用 |
| :--- | :--- | :--- |
| **用户权限** | **用户命名空间 (`userns-remap`)** | 将容器内 `root` 映射为主机上的非特权用户，防止权限提升攻击。 |
| **文件系统** | **命名空间 + UID 重映射目录** | 每个租户的数据存储在独立的、仅由其自身可读的目录中。 |
| **网络流量** | **网络命名空间 + 自定义网络** | 每个租户拥有独立的网络栈和 IP 地址，实现网络流量隔离。 |
| **计算资源** | **控制组 (cgroups)** | 精确限制每个租户或容器的 CPU、内存、磁盘 I/O 用量，避免资源争抢。 |
| **系统调用** | **Seccomp / AppArmor / SELinux** | 进一步限制容器可执行的操作，缩小攻击面。 |

通过上述技术组合，管理员可以在共享的 Docker 宿主机上为不同团队或成员构建出安全、相互隔离的虚拟环境。
这种分离叫什么？
这种分离机制在技术领域有多个专业术语，根据上下文的不同，侧重点也有所区别：

## 🎯 最核心的术语

### **容器化** (Containerization)
这是最上层的概念。Docker 本身就是一种容器化技术，它通过操作系统级别的虚拟化，将应用程序及其依赖打包在一个个相互隔离的环境中运行。

### **多租户隔离** (Multi-tenancy Isolation)
这是从**业务和管理角度**最准确的术语。当多个团队（租户）共享同一个 Docker 宿主机时，这种分离就叫多租户隔离。它强调的是多个"租户"（可以是不同部门、公司成员、项目组）在同一基础设施上的共存与隔离。

---

## 🔬 从技术实现角度的术语

### **命名空间隔离** (Namespace Isolation)
这是 Linux 内核层面的技术术语。Docker 正是通过创建独立的命名空间来实现资源视图的隔离：
- **PID namespace**：隔离进程 ID
- **NET namespace**：隔离网络栈
- **MNT namespace**：隔离文件系统挂载点
- **USER namespace**：隔离用户权限（这是实现安全多租户的关键）

### **控制组隔离** (Cgroups Isolation)
侧重于**资源分配和限制**的隔离，确保各租户不会相互影响对方的计算资源。

### **沙箱化** (Sandboxing)
这是一个形象化的术语，指将每个容器运行在一个"沙箱"中，限制其对宿主机和其他容器的访问能力。

---

## 🏢 在企业运维场景中的术语

### **租户隔离** (Tenant Isolation)
这是**企业级运维中最常用的术语**。当 sysadmin 说"我们实现了租户隔离"，意味着：
- 不同公司成员/部门在 Docker 环境中被视作不同的租户
- 每个租户拥有独立的网络、存储、资源配额
- 一个租户无法访问或影响另一个租户的数据和容器

### **工作负载隔离** (Workload Isolation)
侧重于**应用层面**，指不同的应用工作负载（如开发环境、测试环境、生产环境）在 Docker 宿主机上被隔离运行。

### **权限边界** (Permission Boundary)
从**安全角度**的术语，描述的是通过用户命名空间等技术划定的安全边界，确保即使一个租户的容器被攻破，攻击者也无法跨越这个边界影响其他租户。

---

## 💡 总结：你应该使用哪个术语？

| 场景 | 推荐术语 | 原因 |
|------|---------|------|
| 向非技术人员解释 | **多租户隔离** 或 **容器化** | 通俗易懂，能清晰表达"多个团队共享一台机器但互不影响"的概念 |
| 技术讨论/文档 | **命名空间隔离** + **用户命名空间重映射** | 精确描述底层实现机制 |
| 企业运维/架构汇报 | **租户隔离** | 符合企业语境，强调业务层面的隔离 |
| 安全审计/合规 | **权限边界** 或 **沙箱化** | 强调安全防护效果 |

在你描述的 sysadmin 使用 Docker 与公司其他成员分离的场景中，最准确、最专业的说法是：

> **"基于用户命名空间的多租户隔离"** (User Namespace-based Multi-tenancy Isolation)

这个术语既涵盖了技术实现（用户命名空间），又明确了业务场景（多租户），同时暗示了安全隔离的层级（权限边界）。

你提到的缩写，最有可能就是 **GPUaaS**。

它由 GPU + aaS（即 “as a Service”，作为服务）组成，是这个场景下最常用、最标准的术语[citation:6][citation:1]。这个词精准地描述了你们公司“将GPU集群作为一种共享服务，供不同成员或团队按需访问”的模式。

除了 **GPUaaS**，根据你们具体实现方式的不同，可能还有其他几个相关的缩写或关键词：

| 缩写 / 关键词 | 核心概念 | 解释与在GPU集群中的应用 |
| :--- | :--- | :--- |
| **MIG** | **多实例GPU** | 这是NVIDIA的一项硬件级虚拟化技术，允许将一块物理GPU切分成多个完全隔离的独立实例[citation:8][citation:9]。它能确保一个租户的计算任务既看不到也影响不到同一块卡上其他租户的任务，实现最强级别的隔离[citation:3]。 |
| **vCluster** | **虚拟集群** | 在Kubernetes的世界里，vCluster可以在一个物理集群之上创建多个“虚拟”的控制平面。每个团队都能拥有自己“独立”的K8s集群体验（比如可以自由安装自己的软件），但底层共享着同一个GPU资源池，兼顾了隔离性和资源利用率[citation:2]。 |
| **RBAC** | **基于角色的访问控制** | 这是K8s中用于管理权限的核心机制[citation:3][citation:10]。它可以精细地定义“谁”（哪个成员或团队）能在“哪个命名空间”里对“哪些GPU资源”做“什么事”（创建、删除等），是逻辑隔离的基础[citation:5]。 |

“多租户”（Multi-tenancy）是描述这类架构的核心术语，而 **GPUaaS** 是它在商业化或服务化场景下的具体体现。对于GPU这种昂贵的资源，要实现高效的 **多租户隔离**，通常会综合运用上面提到的所有技术：用 **MIG** 在硬件层面切分，用 **vCluster** 在管理层面隔离，最后用 **RBAC** 统一控制权限。
mig是怎么用的
MIG (多实例GPU) 的使用分为三个核心步骤：**① 硬件检查与模式开启 → ② 查看可选配置方案 → ③ 创建并分配实例**。整个过程通过NVIDIA官方的`nvidia-smi`命令行工具完成，对硬件有严格要求。

### 🛠️ 第一步：硬件检查与模式开启

MIG是高端数据中心GPU才有的功能，操作前必须先确认硬件支持。

1.  **检查GPU型号与当前状态**
    运行 `nvidia-smi`，查看输出中的关键信息：
    - **“MIG M.”** 一栏：显示 `Disabled` 表示未开启。
    - **GPU型号**：必须是A100、H100、B200等NVIDIA Ampere或更新架构的数据中心GPU（消费级的RTX 30/40系列**不支持**）[citation:1][citation:7]。

2.  **停止监控服务（重要）**
    开启MIG需要重置GPU，任何使用GPU的进程都会导致操作失败。**必须先停止可能占用GPU的服务**，如`nvsm`、`dcgm`等，否则命令会报错[citation:2][citation:3]：
    ```bash
    sudo systemctl stop nvsm dcgm
    ```

3.  **开启MIG模式**
    使用以下命令为目标GPU（`-i 0`表示第一张卡）开启MIG。命令执行后GPU会重置，这是正常现象[citation:3][citation:9]：
    ```bash
    # 为0号GPU开启MIG模式
    sudo nvidia-smi -i 0 -mig 1
    ```

4.  **验证是否生效**
    再次运行 `nvidia-smi`，确认“MIG M.”一栏显示为 `Enabled`。

### 🗺️ 第二步：查看可用的切分配置方案

开启MIG模式后，GPU就可以被“切割”了。切割的方案有标准模板，称为**Profile**[citation:1]。
